# Правила работы агентов

Эти правила действуют для всего репозитория. Это рабочий процесс, **не песочница безопасности**: права инструментов и подтверждения команд настраиваются в клиенте агента, доступ к репозиторию, обязательное ревью и защита веток — на Git-хостинге. Наличие файла не включает эти ограничения автоматически.

Обязательные инструкции: [API_CONVENTIONS.md](API_CONVENTIONS.md) и [TEAM_WORKFLOW.md](TEAM_WORKFLOW.md). Перед API-задачей прочитай образец `src/modules/notes/openapi.yaml`, реализацию `src/modules/notes/`, `tests/notes.test.ts` и `scripts/notes-smoke.ts`; не создавай альтернативные соглашения.

## Перед изменениями

- Прочитай задачу, README, обязательные документы выше и затронутый код. Зафиксируй цель, границы, не-цели, входы/выходы и проверяемые критерии приёмки. До работы нужен один реальный Issue Assignee и явные файловые границы по TEAM_WORKFLOW. Не расширяй задачу самостоятельно; неоднозначный контракт согласуй с captain (первоначально владельцем репозитория).
- Найди и используй существующие паттерны. Делай минимальное законченное изменение; не включай посторонние рефакторинги, переименования и форматирование. Не перезаписывай чужую работу. При параллельной работе заранее согласуй владельцев файлов.

## Код и границы

- Node.js >=24, ESM, pnpm 12.14.0; источник версий — `package.json`. Приложение запускается Node нативно: только стираемый синтаксис, относительные импорты с `.ts`, типы через `import type`. Vitest преобразует тестовый TypeScript отдельно; не добавляй транспиляторы в запуск приложения, алиасы, `enum` или parameter properties.
- Сохраняй строгий TypeScript и текущие проверки. Не прячь ошибки через `any`, необоснованные приведения, `@ts-ignore`, отключение правил или ослабление конфигурации.
- `src/app.ts` экспортирует фабрику `createApp(db)` без открытия порта; `src/server.ts` отвечает за запуск HTTP-сервера. Новые API-модули находятся в `src/modules/<module>/` со своим `openapi.yaml`, legacy-маршруты — в `src/routes/`, Pug — в `views/`, статика — в `public/`, отдельные тесты — в `tests/`. Зависимости внедряются; не создавай PrismaClient на запрос и не переноси запуск сервера в импортируемые модули. Общие файлы меняет captain по запросу в Issue.
- Сохраняй существующие HTTP-статусы, заголовки, тела ответов и HTML-обработку ошибок, если задача явно не меняет контракт. Не создавай новые слои и зависимости без необходимости.
- Единственный test runner — Vitest. Добавляй тесты в `tests/**/*.test.ts`, используй явные импорты из `vitest`, сохраняй изоляцию от `.env`, запрет `.only` и очистку ресурсов. `pnpm test` — однократный запуск, `pnpm test:watch` — watch; строгую проверку типов выполняет `pnpm check`.
- Конфигурация сервера определяется Zod-схемой в `src/config.ts`; не читай новые env-поля по всему приложению и не вводи скрытые fallback. Входы API валидируй строгими Zod-схемами на границе и используй только успешный результат; выводи типы через `z.infer`. Общие HTTP-правила, ошибки RFC 9457 и разделение `/api`/legacy определены в API_CONVENTIONS; endpoint-specific контракт веди в `openapi.yaml` модуля и обновляй вместе с поведением.

## Согласования и безопасность

- Без явного одобрения тимлида не меняй зависимости/lockfile, публичные API-контракты, переменные окружения и их значения по умолчанию, CI, разрешения и защитные настройки. Не ослабляй проверки, frozen install или запрет непроверенных install scripts ради зелёного результата.
- Не удаляй, не пропускай и не подменяй тесты ради прохождения проверок; не используй `.only`, фиктивные проверки и скрывающие ошибки fallback. При изменении поведения обновляй реальные тесты и соответствующую документацию в рамках задачи.
- Не читай и не передавай агентам, внешним сервисам, логам, issue или PR реальные секреты и содержимое `.env`. В `.env.example` допустимы только безопасные примеры. При обнаружении утечки сообщи тимлиду без повторения секрета; секрет необходимо отозвать/заменить.
- Тесты должны быть изолированы от локального `.env`, не зависеть от внешних сервисов и освобождать открытые серверы/ресурсы.
- Одна задача — одна ветка/worktree, отдельные dev-БД и порты. Общие файлы, schema/миграции и lockfile не редактируй параллельно: порядок интеграции и разрешения конфликтов определён TEAM_WORKFLOW. Не форматируй общие файлы целиком из модульной задачи.

## Перед передачей результата

- После завершения и интеграции всех изменений назначенный интегратор выполняет `pnpm verify` целиком: проверка форматирования Oxc → lint → типы → Vitest → сборка. Исполнитель делегированной части не запускает проверки во время правок; передаёт интегратору необходимые команды. Не заменяй полный verify набором выбранных проверок и не исправляй сбой отключением этапа.
- Интегратор выполняет реальный smoke запущенного приложения по README: `/`, `/users`, `/stylesheets/style.css`, неизвестный legacy URL (HTML 404), неизвестный `/api` URL (Problem 404), а также изменённый сценарий. Для Notes создание/чтение/удаление проверяется с настоящим PostgreSQL. Проверь фактические статусы и содержимое, затем останови свой сервер. Наличие теста не означает, что smoke выполнен.
- Если работу разделяют агенты, исполнитель не запускает проверки параллельно с чужими правками: после интеграции назначенный ответственный выполняет полный verify и smoke перед общей передачей.
- Отчёт короткий: что изменено; ссылка на задачу; затронутые контракты/env/зависимости и согласование; точные выполненные команды и результаты; smoke с URL/статусом/наблюдением; оставшиеся риски. Невыполненную проверку явно отметь с причиной, не объявляй её успешной. Перед merge нужен человеческий review; изменение перечисленных выше границ проверяет тимлид.
